# Harness 维护与发布

Version: 0.3.0

本文件面向用户、父助手与 Host 操作者，不加入 input manifest。研究目标与行为原则在 SOUL，接口与状态技术事实在 execution；文档职责与装载链见 [Agent 输入管理](../reference/agent-inputs.md)。

## 夜间研究与白天维护

夜间由单个 Agent 自主研究 Policy、采集、训练、评估与分析结果。白天由人类和 Codex 依据原始执行轨迹维护 Harness，包括模型调用、工具、上下文、记忆机制、调度与恢复。Agent 负责报告过程问题及证据，并继续修改研究代码和管理研究知识。

维护者从执行轨迹、Gateway 请求记录、模型用量和 Controller 作业记录定位问题，保留当时输入和版本。先用相同输入复现，再修改、回归并记录版本。保留原 run 的 checkpoint、工作区和在途远程作业；恢复后核对实际加载的版本和首个相关调用。按下文审批流程发布输入或恢复。常规窗口见[夜间运行窗口](#夜间运行窗口)。

日间复核从同一研究身份的 `trajectory.jsonl`、`model-usage.jsonl`、`gateway-events.jsonl` 和 Controller 作业终态入手。按症状选择可重复的失败序列，用受控状态验证修复，再用正式夜间日志核对真实调用次数、耗时和研究产出。输入 token 与缓存命中分别统计。工具等待产生的 Host 请求属于基础设施流量，模型唤醒次数由 Responses 请求记录核对。

### 原地发布新版 Harness

白天完成验证后，选择已推送到 `origin/main` 的完整 Git 提交 SHA。交接 Markdown 只写 `## 已核对结论` 和 `## 待办`，每节至少一项。为结论附实验报告与版本，为待办附原作业 ID、checkpoint 或已经授权的资产引用。

用最初绑定定时启动器的 run 作为锚点。先预览，再用返回的摘要确认发布：

```bash
uv run python -m a3_research_agent.cli.night_release "trajectories/<开始时间>" \
  --commit <已发布提交SHA> --handoff <交接.md>

uv run python -m a3_research_agent.cli.night_release "trajectories/<开始时间>" \
  --commit <已发布提交SHA> --handoff <交接.md> --confirm <发布摘要>
```

确认固定启动命令、Git 提交、三个 prompt、研究 skills 和交接正文。21:00 有待发布版本时，定时器在暂停的原 run 上应用发布，再恢复同一主身份和研究工作区。Harness 从固定 Git 提交只读加载；对话、checkpoint、记忆、skills、计划和作业台账继续使用原文件。升级前归档旧源码指针、输入版本和 checkpoint 边界，交接正文通过独立 feedback ID 与 SHA 登记。未发布新版时直接恢复当前 run。

轨迹、作业归属和产物留在原处，远程在途作业继续执行。Agent 继续使用原身份管理这些作业，在新作业里用只读快照复用历史资产。遇到仍不可读的依赖时，Agent 停止受阻研究线并向操作者报告。若 Mac 重启，用原锚点重新启动定时器；它按锚点选择已发布版本及当前 run。迁移后的发布记录位于 `.runtime/night-window/<锚点run>/`。

也可在维护窗口离线应用已冻结的发布，再按原来的启动命令恢复：

```bash
uv run python -m a3_research_agent.cli.apply_release "trajectories/<开始时间>" \
  "<冻结发布目录>" --digest <发布摘要>
```

原地升级要求 run 已暂停并取得排他锁。普通恢复沿用原模型；明确应用发布时，可采用当前部署配置中的模型与参数，并归档前值。升级事务未完成时，普通恢复会停止并保留现场；用同一发布摘要继续处理。


## 低频弱监督与批准边界

正式运行前由部署方完成执行环境预检与预算配置；预算可分别设置限额或明确不限，实际配置留档。研究 Agent 自主提出实验、比较候选、处理研究代码错误并分析结果，持续提高 2×5、2×10 全量评测的准确率与通过率。外界按实际进展低频查看摘要、轨迹、资源和阻塞；只在出现明确问题或有用的新信息时提供范围清晰的反馈，不逐步代替 Agent 设计和指挥全部实验。反馈附原始证据和来源，操作者依据实际执行结果复核研究进展。

每次热加载或中断前须获得用户明确批准，包括热加载输入、热加载反馈，以及停止/暂停运行来应用改动。父助手先说明目标 run、拟发送的具体内容或版本、理由、受影响身份/作业、预计影响和恢复方式；批准后只执行该范围。一次代码修改批准、先前的热加载批准或笼统的持续优化意向，不自动批准下一次运行干预。单纯查看状态或预览并不发布内容，也不能据此视为获准。摘要或目标身份变化时重新确认批准是否仍覆盖实际操作，不擅自扩大范围。

审批由外界用户与操作者负责；不让研究 Agent 审核外界是否获批，也不把本文件或审批流程复制进研究提示词。Agent 只需按当前输入、实际权限及收到的反馈核查并记录自身决定。

反馈说明观察、来源、适用范围与建议。评测设置发生变化时，记录新旧模型、数据、种子与计分条件，让结果保持可追溯和可比；历史报告保留当时设置。研究报告记录实际人工参与。

## 人工干预必须说明

任何人工干预都应通过 human feedback 向受影响的研究 Agent 讲清楚，尤其是人工恢复、外部修复、输入更新和调度改变。说明实际改了什么、为何干预、哪些未改、证据与不确定性，以及希望它重新核对什么和继续什么；不能只改变进程或磁盘状态，假设 Agent 自然知道。没有活跃进程时，仅对仍符合恢复条件且经批准继续的任务，在恢复入口带入反馈；不为发送通知复活已完成任务；运行中按已批准的反馈入口投递。当前机制仅绑定一个主身份，涉及接任时须核对接收身份与交接材料，不假定自动广播。

该要求不授予新的干预权限，也不要求只读观察都注入反馈；仍遵循每次实际干预的明确批准。登记之后核对 forwarded 事件和对应模型调用的 human_feedback_ids，区分“已登记”“已送达”“已采纳”，没有送达时如实说明。基础设施检查和修复记录与科学评测结果分别保存。

## 热加载版本化输入

按 [版本规则](../reference/agent-inputs.md#版本与发布记录) 修改源文件并递增版本；编辑不会自动影响运行中的实验。先预览：

```bash
uv run python -m a3_research_agent.cli.reload_inputs "trajectories/<开始时间>"
```

核对警告、原版本、新版本和内容摘要，将具体变更与影响交用户批准；获批后使用预览返回的完整摘要发布：

```bash
uv run python -m a3_research_agent.cli.reload_inputs "trajectories/<开始时间>" --confirm <预览摘要>
```

更新内容来自当前仓库的三个 prompt 和研究 skills。Host 检查完整输入清单、UTF-8、符号链接、版本和内容摘要，旧 revision 继续保留。此入口更新只读部署输入；工作区中的技能副本与索引由 Harness 安装流程维护。

确认绑定具体文件内容，预览后源文件变化会使旧摘要失效。操作者认证保存在 Host 私有状态，Agent 令牌不能更新输入。已发出的模型请求按旧版本返回，下次请求使用新版本；原对话与 Agent 代码不重写。热加载不会重建已有 Python 对象、切换模型或镜像；运行参数和固定基础设施代码变更通过停止/恢复应用，相关中断也须事先获批。

发布后检查 input manifest 的 active、revision/generation 和 input-events；按对应模型用量的 input_revision 核对实际采用版本。失败或回滚如实记录，不声称已生效。更多快照与历史记录见 [输入管理](../reference/agent-inputs.md#发布-harness-与恢复)。

## 恢复时加入人类反馈

恢复或为恢复而中断前，按上文确认用户批准的范围。环境修复说明或专家建议可以维护在同一个本地 `human-feedback.md` 中，每次覆盖内容。反馈文件由人类明确授权注入，普通历史报告与工具输出继续按数据处理。

```bash
bash scripts/start-rsi.sh \
  --resume-from "trajectories/<开始时间>" \
  --feedback-file human-feedback.md
```

`--feedback-file` 仅用于恢复已经生成 Harness 的主 Agent；未提供时不会读取该源文件。当前实现要求 Harness 向 Gateway 发送完整消息历史，不支持仅用 `previous_response_id` 引用服务器端对话。反馈应说明已核实的变更、受影响作业与建议核查事项，不包含认证信息，并保留实际评测结果。

Host 读取当次 UTF-8 文本（最多 64 KiB），保存内容副本、SHA256 和反馈 ID，封装协议版本为 0.1.0。源文件不要求人为维护语义版本；每次显式注入的具体内容由摘要与反馈 ID 标识。同一身份最近一次反馈与文件内容一致时，重复指定不会新建注入事件。覆盖源文件不会自动改变正在运行的请求。

恢复后，反馈作为一条新的 user message 放在原有历史之后、下一次模型调用之前。Host 不改写旧 checkpoint、工具结果或原始轨迹，不拆开 function_call 与对应工具结果。暂停进程可能仍在处理恢复前的请求；反馈是否实际抵达，以后续模型请求的 human_feedback_ids 和 Host 的 forwarded 事件为准。forwarded 表示模型请求成功返回，不代表 Agent 已接受建议或完成了建议动作。

后续完整历史请求中，Host 在同一个历史边界保留该条反馈，每份有效上下文只有一条该反馈，不在每轮末尾反复追加。再次 resume 不指定文件仍会沿用已经登记的反馈。Harness 压缩或重建上下文时，Host 将反馈重新定位到当前完整历史末尾并记录 reanchored 事件；未完成的工具结果须先对齐。

同一个源文件便于维护，当次副本与事件仍保存在本 run 私有的 `.host/human-feedback/`，恢复与审查依赖这些记录。反馈绑定登记时的主身份。原 run、身份和 Agent 的持久记忆保持不变，实验报告应记录实际人工参与。

## 运行中热加载人类反馈

Host 已运行新版反馈接口时，可以让实验继续执行，通过独立终端把同一个 `human-feedback.md` 中的最新内容送给当前主 Agent。先预览：

```bash
uv run python -m a3_research_agent.cli.reload_feedback "trajectories/<开始时间>" \
  --feedback-file human-feedback.md
```

命令显示正文、接收身份与摘要，尚不注入。核对正文、身份、摘要并取得本次用户明确批准后，使用显示的摘要确认：

```bash
uv run python -m a3_research_agent.cli.reload_feedback "trajectories/<开始时间>" \
  --feedback-file human-feedback.md --confirm <预览摘要>
```

正文或主身份变化会使旧摘要失效，须重新预览。操作仅限持有 Host operator 凭据的人类入口；普通 Agent 无权注入。源文件最多 64 KiB UTF-8，覆盖文件本身不会自动发送。Host 已暂停或仍运行旧代码时，需要先按正常流程恢复或重新部署；CLI 不会替你启动实验。

登记后，反馈会出现在当前主 Agent 下一次完整历史模型调用中。已发出的模型请求、工具和远程作业继续执行，不会即时打断。返回 `delivery=next_model_request` 表示登记成功、等待投递；可在 `.host/human-feedback/events.jsonl` 找到对应 `forwarded`，并在 `model-usage.jsonl` 用 `human_feedback_ids` 核对实际成功转发。主身份若在投递前退出或交接，反馈仍保留在原身份的记录中，不自动广播或改发。

内容留档、去重、恢复后沿用、工具结果配对及人工参与记录，与恢复时反馈共用同一机制。

## 干预后的核对

只核对本次操作是否生效及是否造成阻塞：输入发布检查生效清单，反馈检查登记和成功转发事件，中断检查实际进程/作业状态与恢复材料。建议是否采纳及其研究效果，以 Agent 后续行动和评测记录核对。若未投递、身份已交接或需要再次中断/热加载，先说明实际状态和下一步，再取得相应批准；不自动改发给另一身份或重复干预。

## 可选网页能力的配置与发布

网页网关默认关闭，部署方在 Host 的 `.env` 配置 Tavily 凭据和启用选项，再发布对应工具实现。配置入口见[网页研究](setup.md#网页研究)。输入热加载只更新提示词；工具实现通过暂停期间的 Harness 发布应用。

搜索和正文提取不设 per-run 累计次数上限，持久计数跨恢复保留；提供商账户额度由使用者管理。`web_status` 只读能力和配置状态。认证或额度错误交由操作者处理，其他离线研究工作可以继续。

## 研究停止与恢复

研究围绕 A3 2×5、2×10 的全量评测表现持续迭代。Agent 记录每轮模型、数据、评测设置与证据，操作者按需要暂停和恢复。正常资源等待由现有 Harness 和 Controller 处理。

操作者暂停时保留 checkpoint、研究工作区和远程在途作业。恢复先核对原作业状态与已保存结果，继续同一身份；研究结论与既有评测证据保持原始条件。

## 夜间运行窗口

暂停过的 run 可用 `bash scripts/start-rsi.sh --night-window --resume-from trajectories/<开始时间>`
继续运行。窗口固定为北京时间 21:00（含）到次日 09:00（不含）。到点后启动器向 Host
发送正常中断信号，保存 checkpoint 并关闭本地 Agent。远端 Controller 继续执行已提交的
作业。21:00 按发布记录原地升级并恢复当前 run。白天只保留等待窗口的启动器。启动器退出或机器重启后，
需要重新运行该命令。若固定发布版因耗尽模型请求重试而退出，启动器核对当次的上游失败记录和已保存的
checkpoint，在窗口内以 30 秒至 5 分钟的退避间隔接续同一 run。其他退出仍保留现场。可在本地 `.env` 设置
`A3_NIGHT_WINDOW_RUN_ID` 为对应 run 目录名，要求该 run 使用夜间入口恢复。

可在本地 `.env` 设置 `A3_UPSTREAM_RESPONSES_BASE_URL`、
`A3_UPSTREAM_RESPONSES_MODEL` 和 `A3_UPSTREAM_RESPONSES_API_KEY`，让 Host
使用指定的 OpenAI 兼容 Responses 服务。该配置统一应用于 Gateway 的各角色调用，恢复仍
沿用 run 原有的模型身份和适配器标识。模型用量记录的 `response_model` 保存供应商返回
的实际模型。API key 仅供 Host 使用。切换前用最小请求验证端点、模型与凭据。
恢复使用默认 `chatgpt/` 路由时，Host 转换历史中其他供应商生成的消息和工具调用，
保留工具调用与结果的配对，原 checkpoint 保持原样。

`A3_UPSTREAM_RESPONSES_READ_TIMEOUT_SECONDS` 设置 Host 等待该服务响应数据的超时，默认
120 秒，连接超时为 10 秒。处理长上下文时可在 `.env` 调高读取超时，并核对 Harness
对应接口的等待时间。恢复 run 后加载新配置。

主 Agent 对模型连接错误、超时、限流和临时服务错误重试，等待间隔从 5 秒递增到最多 2 分钟。
每次重发同一决策请求，保留已提交的作业和已保存的工具结果。Host 记录上游原始 HTTP 状态码，
客户端请求、鉴权和输入长度错误直接报告。运维暂停和夜间窗口结束时可中断等待。
